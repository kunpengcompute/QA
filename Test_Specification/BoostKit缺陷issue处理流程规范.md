# **一、目的**
为规范BoostKit社区上缺陷类issue提单要求，确保缺陷类issue所填信息准确有效，各责任人处理及时，且对缺陷的修改不引入新问题，不断夯实社区版本质量，特制定本规范。
# **二、范围**
本规范适用于BoostKit开源社区所有开发者
本规范统一由BoostKit QA sig组进行维护、更新
# 三、issue处理流程
为提升缺陷issue处理效率，标准流程主要分为以下7步：
- 提交issue
- QA sig组审核
- 特性所属sig组审核
- 开发人员根因分析
- 开发人员实施修改
- 代码review&合入
- QA sig组组织验收
- 测试人员回归验证


## 1、issue状态

- 待办的
- 已确认
- 修复中
- 已完成
- 测试中
- 已验收
- 挂起
- 已取消

### 2、提单要求

 在Boostkit的版本周期内，所有问题都必须提缺陷issue处理

 - 提交缺陷issue按照要求：

    1. 必填项【标题描述】、【测试类型】、【测试版本】、【操作系统和硬件信息】、【测试环境】、【操作步骤】、【实际输出】、【日志信息】、【提单组织】、【Issue优先级】

    1. 选填项【问题描述】、【被测功能】、【预置条件】、【预期输出】、【测试代码】、【团队】
     
** **以上信息需填写完整，QA sig组审核不通过，则退提单人** **

  问题确认过程中涉及开发定位人员变更的，由首问开发人员负责协调


### 3、issue开发处理原则
+ 已提交的issue，开发人员存在异议或认为需要补充修改的，双方人员沟通无误后，由issue提交人负责修改
+ issue处理时，文档需同步更新；
+ 主要和严重问题建议由PL或SE进行集体讨论，保证修改方案可靠、问题解决彻底
+ issue问题合入前，需进行充分自验证，有完整自验证截图，pr满足门禁要求
+ 问题定位超过3个工作日的主要、严重问题，及时启动攻关，保障问题及时定位解决
+ 对于重复issue，需要等重复的问题单修改验证完成后才可以处理
+ 涉及issue取消操作的，参考6、缺陷issue取消原则


### 4、issue关闭原则

+ 转测要求：
   开发人员采用转测版本自验证，转测时需附上自验证截图（包括版本、关键步骤等），否则驳回转测申请

+ 回归要求： 
  - 开发白盒自提单：
     在开发人员写明问题和场景后，允许开发人员关单
  - 测试及社区人员提单：
    需经测试人员回归验证后关单。测试人员回归验证完成，在评论中回复验证结论、验证版本及操作步骤，证明问题已得到解决，且没有产生新问题，确认无误后issue关闭（issue状态设置为已验收）。

  ** **issue必须通过回归测试方可到‘已验收’状态；****
   
### 5、issue回归不通过原则
+ 如下场景判断为issue回归不通过：
  1. 未解决issue中明确描述的所有问题；
  2. 开发在未解决issue版本中走到测试；issue中或测试明确告知需要配套修改文档资料但开发人员未完成修改

+ 如下场景判断为issue回归通过：
  1. 回归中发现非修改引入/非解决不彻底导致的新增场景问题，且有新的issue跟踪
  2. issue中描述一类问题，没有详细枚举，回归测试版本中绝大部分已解决，小部分存在问题

+ 回归测试不通过情况下，测试人员应事先和开发人员进行沟通，避免受操作配置等问题影响。严禁在流程中反复提交和变更结论。测试和开发对于回归测试结论不能达成一致意见时，经过特性sig组评审决策
+ 开发组针对回归不通过问题组织质量回溯或AAR，持续改进（内部）
### 6、issue取消原则
+ 非问题、问题现象一致的重复问题、无法联系到提单人且无法复现的问题，可撤销，撤销原则如下：
  1. 与提单人确认为非问题/重复问题的issue，由提单人撤销；
  2. 若联系不到提单人，需要通过社区公告向community、问题所属sig组和QA sig组公示7天，允许以非问题撤销，由QA sig组负责撤销。
  3. 联系不到提单人、且按照issue中描述的操作步骤无法复现问题（至少复现20次）的场景，通过社区公告向community、问题所属sig组和QA sig组公示7天，允许撤销此问题。之后提单人如有异议，可重新打开此issue，并在issue中补充可复现的测试步骤、可供定位的堆栈日志等详细信息，由QA sig组负责撤销。
  
 **无论是何种情况，对于需要转非问题的issue，应知会到相应的模块leader并征得同意，由QA sig组maintainer确认后修改状态，不得自行更改状态**


### 7、issue遗留/转需求原则
issue遗留问题，需提交对应特性sig组评审裁决，并需给出影响性分析、有效规避措施：
+ 社区当前版本无法解决、且非阻塞性问题，可经过sig裁决遗留到下个版本解决
+ 社区当前版本解决成本较高、且对质量影响不大的问题，可经过sig裁决遗留到下个版本解决
+ 长期不复现、但未降级至“已取消”状态的问题，可经过sig组裁决遗留到下个版本解决

**issue转需求问题，提交对应特性sig组评审裁决后，可将issue类型设置为“需求”**

## 四、缺陷类issue优先级定义

| 优先级               | 定义                                                        |
| -------------------- | ----------------------------------------------------------- |
| 严重 Serious         | 安装/升级/编译失败；coredump；关键指标低于基线30%以上；数据丢失或数据不一致等问题； |
| 主要 Main            | 特性要求的规格未实现；关键指标低于基线20%及以上；根据资料指导造成错误操作（如按照安装指导造成安装失败） |
| 一般 Secondary       | 特性要求的规格实现有问题，但未造成整个特性功能失效；关键指标低于基线10%；易用性差；资料缺失少内容 |
| 不重要 Optional      | 官网文字排版风格问题；资料可读性差、用词不当、错别字及不易于理解的问题；操作维护功能存在冗余信息、无效命令； |
| 无优先级 No priority | 不推荐，未指定优先级，请按上述定义指定优先级                 |
